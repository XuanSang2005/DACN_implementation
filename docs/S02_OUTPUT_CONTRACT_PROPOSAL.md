## 2. Quy ước kiểu, identity và export

Các bảng/signature trong tài liệu là đặc tả trường đầy đủ. **Mọi trường bắt buộc**, trừ trường có hậu tố `?`; `T|null` vẫn bắt buộc có key. Không nhận key lạ. `[]` nghĩa không có phần tử được ghi, không mặc nhiên “đã kiểm và không có vấn đề”. Trạng thái `not_run`/`not_assessed` phân biệt chưa làm. Không dùng `null` cho danh sách. `null` chỉ có nghĩa đã ghi riêng ở bảng (chưa biết/chưa tạo/không áp dụng).

`ID` là chuỗi ASCII opaque `[A-Za-z0-9][A-Za-z0-9._:-]{0,127}` do code cấp; production khuyến nghị UUIDv4, ví dụ dùng ID dễ đọc. Đây chỉ là metadata S02, không siết ID người dùng của S01. ID record duy nhất toàn kho; ID phần tử logic duy nhất trong session, được giữ giữa model revisions khi cùng khái niệm, không tái dùng cho đối tượng khác sau xóa. ID của nested workflow node/edge, mapping part, option, condition cũng phải duy nhất trong phạm vi record chứa chúng. `Text` là string có ít nhất một ký tự ngoài W29 của S01; không trim/normalize. Nhãn nguồn được giữ nguyên. `Int` là JSON integer, loại boolean; `Time` UTC millisecond; `Digest` 64 hex thường SHA-256 trên **bytes artifact lưu**, không dùng làm bằng chứng ngữ nghĩa.

`Record = {type: enum ở mục 4–10, id: ID, created_at: Time, body: object theo type}`. Record bất biến; `created_at` do code ghi, không dùng sắp revision. Export production có đúng `{contract_version:"s02/0.1.0-draft.3", session_id:ID, records:Record[]}`. Resolver theo kho/session, không chỉ theo file export. Các tham chiếu vận hành `EventRef={command_id:ID,event_id:ID}` và `StageRef={command_id:ID,blob_id:ID}` resolve qua operation/event/staging lookup, không giả là Record IDs. Export bundle phải kèm bản sao các event/staged bytes được tham chiếu và manifest hash; export records đơn lẻ cần lookup chúng. Thiếu record được tham chiếu là lỗi; export đơn lẻ có thể cần lookup phần còn lại. Bản đầu chỉ nhận exact contract version, không tự giả định tương thích minor/draft khác.

File minh họa dùng wrapper riêng `{illustration:"minh họa chưa thực thi", contract_version, session_id, external_bindings:Binding[], records:Record[], scenarios:object[]}`; không phải input production. `Binding={id,type,file,pointer}` trỏ artifact/record hoặc định nghĩa giả định trong scenarios (type phải ghi hypothetical/projection khi chưa là record); đường dẫn tương đối file hiện tại, pointer từ root file. Không coi Binding là nguồn đã trusted lookup. `scenarios` là biến thể/kỳ vọng tài liệu, không là records đã commit. Không import wrapper này như kết quả thật.

Không dùng confidence làm acceptance. Có thể hiện nhãn “needs clarification” trên UI bên cạnh origin, không thay thế origin.

Hai criteria giống text vẫn là hai mục. Reorder làm snapshot mới; không nối bằng index/text. So sánh values để gợi ý tác động không quyết định identity criterion.

## 3. Cổng nhận S01 và bản sao nguồn có thẩm quyền

Adapter nhận cấu hình kho local và `s01_run_id`, tùy chọn `expected_snapshot_id`. Thực hiện:

1. `Repository.verify()` và `get_run()` của package baseline đã pin; không gọi `initialize()`/`submit()` hoặc đọc JSON tự nhận validated. Receipt chỉ cung cấp định danh để lookup.
2. Kiểm output contract exact, `status=validated`, mọi checks passed, handoff true và snapshot_id khớp; `check_envelope()` bổ sung nhưng không thay checked lookup. Input schema/hash thuộc allowlist baseline.
3. Dùng đúng snapshot từ run; đối chiếu `expected_snapshot_id` nếu có. Không gọi get_head để thay nguồn. Lookup creator/origin và source của run qua API đã kiểm; không sửa metadata validator/timestamps.
4. Archive envelope exact JSON bytes đã serialize qua codec, schema artifact và raw bytes của nguồn run + nguồn tạo snapshot (dedup nếu cùng ID) trong kho S02. Với baseline chỉ hỗ trợ schema1.0.0 đã pin, đọc artifact schema từ package S01 bằng `schema_resource.read_schema_bytes()` và đối chiếu digest của envelope; không cần API SQL đọc bảng riêng S01. Bytes envelope là bản serialize chính xác của giá trị lookup, không tuyên bố giữ nguyên thụt dòng của một file export; bytes raw source thì giữ nguyên tuyệt đối. Chỉ chụp nguồn được chọn, không copy DB/dataset. SourceContext commit cùng các archive cần thiết. S01 history bất biến nên đọc thêm bằng ID không lệ thuộc head có tiến lên; phát hiện sửa trái phép giữa các reads thì failed, không tự hòa giải.

`SourceContext` (`type=source_context`, code tạo trước bước 1, mọi bước dùng): body `{store_key:ID,s01_run_id:ID,snapshot_id:ID,envelope_artifact_id:ID,run_source_artifact_id:ID,origin_source_artifact_id:ID,schema_artifact_id:ID}`. `store_key` là alias cấu hình local, không đường dẫn cá nhân trong model. Spec/revision/origin_source_id/validator/schema versions lấy từ envelope archive, không lặp thành trường có thể lệch. Trong trường hợp unchanged, **run.source.source_id khác snapshot.origin_source_id**, archive cả hai và dùng origin để resolve nguồn của nội dung. Không đọc lại input file theo label.

`Artifact` (`type=artifact`, code tạo; mọi bước dùng): body `{media_type:Text,sha256:Digest,byte_length:Int>=0,purpose:"s01_envelope"|"s01_run_source"|"s01_origin_source"|"schema"|"llm_request"|"llm_response"|"config"|"prompt"|"puml"|"svg",producer_run_id:ID|null}`. Bytes BLOB trong kho theo artifact ID, export là bản sao kiểm hash. null producer chỉ cho archive S01 trước run S02; nguồn gốc archive nằm trong SourceContext. Cùng blob có thể được hai trường source trỏ tới; purpose mô tả mục đích lúc tạo, không đổi bytes. Hash không phải chữ ký; trusted local store là ranh giới tin cậy.

### 4.1 Run

| Trường | Kiểu / ý nghĩa |
| --- | --- |
| `mode` | `live` hoặc `replay`; ví dụ giả lập dùng `replay`, nhãn wrapper ngăn coi là đã chạy |
| `source_context_id`, `config_artifact_id` | ID; cấu hình bất biến được archive, không chứa secret |
| `base_model_id`, `base_analysis_set_id` | ID|null; cùng null chỉ khởi tạo session; còn lại pin cặp context đầu vào |
| `command_id` | ID của operation đã commit trước công việc; không là Record ID |
| `result_analysis_set_id` | ID|null; tập phân tích mới đã commit hoặc null nếu không công bố tập mới |
| `steps` | mảng unique số nguyên 1…9; công việc lần này |
| `status` | `completed`, `blocked`, `rejected`, `failed`, `stale`, `interrupted` |

Attempt chỉ trở thành phần của Run bất biến trong final transaction (§4.3). Request/response raw lưu cả lỗi, không lấy parsed SDK float làm nguồn. Không lưu chain-of-thought; chỉ output nghiệp vụ, lý do thiết kế ngắn và metadata trả về.

### 4.2 Issue và Answer

`type=issue`, LLM/code phát hiện ở 1–6 hoặc 8/review, code lưu; bước 1 gom câu hỏi. Body `{issue_key:ID,supersedes_id:ID|null,model_id:ID,detected_step:Int,kind:"business"|"quality_target"|"analysis_omission"|"design_choice"|"verification",question:Text,reason:Text,trace:Trace,affected:Scope,blocking:Scope,status:"open"|"answered_pending_application"|"resolved"|"withdrawn",answer_ids:ID[],resolution_event_refs:EventRef[],resolution:Text|null}`.

`issue_key` giữ identity câu hỏi, record id là phiên bản nội dung issue; AnalysisSet (§6.1) chọn đúng một record hiện hành mỗi issue_key, kể cả resolved/withdrawn; Bundle không tự chọn subset để giấu issue. affected và blocking cùng model_id; blocking là tập con affected. Chỉ block nghĩa vụ cần thông tin để quyết định, không tự block component chung. `analysis_omission` đọc lại nguồn, không bắt người dùng trả lời lại. `design_choice` đưa ra phân tích/review. `verification` có thể là nghĩa vụ giai đoạn sau; không gọi một câu hỏi nghiệp vụ chưa trả lời là verification để vượt gate. Resolved phải có answer áp dụng hoặc nguồn gốc đã giải quyết được và resolution; không đủ chỉ có text trả lời.

`type=answer`, người dùng cung cấp nội dung, code ghi nguyên văn ở bước 1; body `{issue_id:ID,supersedes_answer_id:ID|null,respondent:Text,recorded_by:Text,text:Text,interpretation:"points_to_existing_source"|"changes_requirements"|"needs_interpretation",existing_source_refs:SourceRef[]}`. `interpretation` là phân loại **tại lúc nhận**, không sửa sau đó; points_to_existing_source cần refs. Draft.2 bỏ hai trường kết quả nullable `s01_update_run_id/new_source_context_id` khỏi Answer, chuyển kết quả sang event áp dụng bên dưới. Không có câu trả lời thì không tạo Answer. Người dùng trả lời mới tạo Answer ID mới, có supersedes_answer_id nếu thay lời cũ cùng issue_key; retry/recovery của lời cũ giữ nguyên Answer ID. Chấp nhận kiến trúc không tự tạo Answer.

### 4.3 Staging trước final Run — F02

**Chọn staging theo operation**, giữ nguyên invariant Artifact.producer_run_id; không nới nullable. Operation là intent bất biến `{command_id:ID,session_id:ID|null,parent_command_id:ID|null,reserved_run_id:ID,request:object}`; request pin loại command, base model/AnalysisSet, nguồn, scope và cấu hình. reserved_run_id là ID dự kiến, chưa là FK tới Run. OperationEvent bất biến `{event_id:ID,command_id:ID,ordinal:Int>=1,kind:Text,payload:object}`; ordinal liên tiếp trong command, không dùng timestamp quyết định thứ tự. Kho kiểm payload theo kind, không nhận arbitrary event từ LLM. Cả hai là records vận hành riêng, không phải Record nghiệp vụ.

StagedBlob gồm `{command_id:ID,blob_id:ID,media_type:Text,purpose:Text,sha256:Digest,byte_length:Int>=0}` và **raw bytes BLOB**; FK tới operation có thật. purpose staging dùng các giá trị Artifact.purpose và thêm `requirement_update_input` cho bytes xin consent; loại thêm này giữ ở staging/event, không promote thành Artifact có purpose lạ. StageRef không được dùng ở chỗ contract đòi Artifact ID. Cùng namespace blob_id bất biến; bytes lỗi parse cũng lưu được. Config/prompt đã tồn tại như Artifact có thể dùng lại qua ID; dữ liệu mới phải staging. Không lưu secret header.

| Mốc commit | Dữ liệu bền vững và references | Chưa có / recovery |
| --- | --- | --- |
| T0 prepare | Operation + staged config/prompt/request + `prepared` event liệt kê StageRefs và attempt ID dự kiến; context lấy từ operation.request; mọi StageRef đã tồn tại | Chưa Artifact/Attempt/Run mới. Receipt biết command_id trước T0. Prepared mà chưa dispatch event: theo giao thức chưa gửi; resume explicit có thể dùng đúng bytes |
| T1 dispatch intent | `dispatch_intent` event chỉ tới prepared event, transport attempt; commit **trước** network send | Crash từ sau T1 đến trước capture đều `unknown_outcome`, kể cả thực tế chưa send; không suy chưa gửi từ thiếu response |
| T2 capture | Staged response bytes + `response_received` event: StageRef, HTTP status, safe headers, requested/returned model, provider_response_id, usage nếu đọc được, elapsed_ms; lỗi parse không ngăn lưu bytes | Chưa official Attempt/Run. Crash sau T2: lookup/recover từ bytes, không gọi provider lại. Nếu capture commit mơ hồ phải lookup command ở connection mới |
| T3 finalize | Trong **một** transaction: promote staged blobs cần dùng thành Artifact + BLOB; tạo final Run chứa Attempt; model/analysis/change nếu hợp lệ; typed links; `finalized` event `{run_id,promotions:[{stage_ref,artifact_id}]}`; cập nhật head | Artifact producer và Run cùng tồn tại khi commit, deferred FK chỉ trong T3. Staging giữ nguyên để audit; không sửa nó thành Artifact. Outcome invalid vẫn có Artifact raw + Attempt invalid_output + Run rejected, không head mới |

T3 có thể tạo Run interrupted/failed từ T0–T2; finalized duy nhất/command, reserved_run_id duy nhất, promotion một StageRef tối đa một Artifact trong command. Config artifact dùng lại giữ producer cũ. Source archive có ngoại lệ producer null như §3; không dùng ngoại lệ này cho LLM/renderer. Renderer cũng staging trước final publish, không giữ write lock khi subprocess chạy. Các vòng refs Run→Artifact→Run hợp lệ vì cùng T3; dữ liệu T0/T2 **không** trỏ tới final Run chưa tồn tại. Invalid candidate không được promote thành Model, nhưng raw evidence vẫn promote.

Lookup command trả trạng thái dẫn xuất `prepared`, `dispatch_unknown`, `captured`, `finalized` hoặc `interrupted`, kèm các IDs đã commit. Không tìm thấy intent không chứng minh hiệu ứng bên ngoài chưa xảy ra nếu receipt/store chưa đối soát. Recovery explicit dùng command cũ và reserved_run_id; thao tác recovery có command riêng parent_command_id trỏ command gốc, nhưng finalization vẫn CAS một outcome cho command gốc. Không tự submit như lần mới. Chỉ khi xác định an toàn và người dùng yêu cầu gửi lại mới tạo attempt/command mới được ghi rõ; unknown provider outcome không được auto resend. Payload event application ở §4.4 bổ sung kinds ngoài vòng LLM này.

### 4.4 Áp dụng cùng một Answer bất biến — F03

**Chọn event chain trên operation đã có**, không tạo Answer giả hoặc sửa Answer cũ. Mỗi application có command_id ổn định, request `{kind:"apply_answer",answer_id,issue_key,base_model_id,base_analysis_set_id,source_context_id}`. `answer_id` và base được pin. Unique một `application_applied` cho mỗi `answer_id` trong kho; selected interpretation event được pin trong kết quả; recovery dùng application command cũ, không là người dùng trả lời mới. Mỗi event dưới đây có EventRef và payload bắt buộc (ngoài event header §4.3):

| kind | payload bắt buộc / điều kiện |
| --- | --- |
| `interpretation_selected` | `{answer_id,interpretation:"points_to_existing_source"|"changes_requirements",explanation:Text,existing_source_refs:SourceRef[],proposed_input:StageRef|null,s01_request:object|null}`. Với changes_requirements, input bytes và request S01 update exact được staging cùng commit; request có spec_id/base_revision. Với existing_source cả hai null, refs không rỗng. Chưa chọn thì Answer needs_interpretation chưa được áp dụng |
| `consent_recorded` | `{answer_id,interpretation_event:EventRef,respondent:Text,text:Text,approved_input_sha256:Digest|null}`. Người dùng xem **toàn input sửa + diff + request base**, xác nhận đúng event/hash; text nguyên văn, không do LLM tự ghi. Changes_requirements cần hash đúng staged bytes; existing-source không đổi nghĩa có thể đi thẳng apply, không bịa consent |
| `s01_dispatch_intent` | `{answer_id,consent_event:EventRef,s01_store_key:ID,s01_run_id:ID,s01_request:object,input_stage_ref:StageRef}`. Commit sau khi đã cấp run ID/ghi receipt S01 theo giao diện S01, trước submit; khớp input/request consent. Không sửa S01 receipt/semantics |
| `s01_result_observed` | `{answer_id,dispatch_event:EventRef,s01_run_id:ID,lookup_status:"validated"|"rejected"|"failed"|"unknown",snapshot_id:ID|null}`. Checked lookup cùng store/run; validated cần snapshot. Rejected/failed/unknown không cho switch hoặc resolved. Lookup không thấy không tự submit lại |
| `application_applied` | `{answer_id,interpretation_event:EventRef,consent_event:EventRef|null,s01_observation_event:EventRef|null,change_id:ID,new_source_context_id:ID,resolved_issue_id:ID}`. Chỉ tạo cùng transaction source switch/model+Change+AnalysisSet+issue resolved, tất cả refs có thật khi commit; existing-source dùng analysis_edit, context cũ và hai event refs nullable nếu không đổi nghĩa |
| `recovery_observed` | `{answer_id,related_event:EventRef,reason:Text}`. Chỉ ghi lần đối soát/tiếp tục; không thay consent, không đổi answer/application identity |

Issue `resolution_event_refs` pin application_applied khi đóng bằng Answer; issue resolved mới supersedes issue pending, answer_ids chứa Answer gốc. Issue giải quyết bằng nguồn sẵn có không có Answer thì resolution ghi SourceRefs qua trace, resolution_event_refs=[] và lý do kiểm được; không gọi câu hỏi nghiệp vụ đã được trả lời chỉ bằng văn bản LLM. Pending/open có resolution_event_refs=[]; không đóng nếu phần nghĩa vụ được hỏi chưa được giải quyết. Nếu input/user consent đã lỗi thời, không rebase tự động: ghi conflict, lấy diễn giải/consent mới đúng input/base; không thay event cũ.

S01 committed nhưng S02 lỗi: application command + dispatch event giữ run ID. Lookup đúng run; sau validated ghi observation (lặp lookup không tạo S01 run), rồi CAS current S02 context để source switch. Nếu S02 đã apply mà mất phản hồi, lookup application_applied trả đúng kết quả, không switch lần hai. Nếu S02 head đã đổi thì cần impact/consent phù hợp trước apply, không gắn nguồn mới vào model cũ. Change.source_record_ids chứa Answer, Issue; `Change.application_event_refs:EventRef[]` nối application_applied. Vòng refs event↔Change↔Issue được kiểm cùng transaction, không deferred sang transaction tương lai. Issue resolved **không** có nghĩa reanalysis/model review hoàn tất; tasks còn pending vẫn chặn handoff.

Diễn giải đang chờ lấy từ interpretation_selected được consent chỉ rõ, không chọn theo timestamp; application_applied pin đúng event được dùng. Trước mỗi dispatch/apply kiểm theo Answer ID đã có applied hay chưa; nếu có chỉ lookup kết quả, không tạo một application nữa bằng interpretation mới. Các command cạnh tranh cùng Answer phải có CAS claim một application hoạt động (bảng application_heads ở kế hoạch); không cho hai command cùng submit. Nếu base S02 đổi, command cũ kết thúc stale, giữ intent/Answer/S01 outcome. Người vận hành mở command tiếp nối cùng Answer, parent_command_id cũ và base mới sau impact review; CAS claim chuyển sang command mới, không sửa request cũ. Nếu S01 đã commit/unknown, command mới bắt buộc nối observation/dispatch EventRef cũ và chỉ lookup/switch, **không dispatch S01 lại**. Consent cũ chỉ dùng nếu exact input/request/diễn giải không đổi; cần thay nghĩa sau một application đã applied thì người dùng phải cung cấp Answer mới, không biến replay thành lời trả lời mới. EventRefs xuyên command chỉ hợp lệ trong cùng Answer lineage. Cơ chế này là đề xuất local concurrency, không tuyên bố API idempotency hoặc exactly-once provider.

## 5. Model và các phần tử bước 2–5

`type=model`, code commit; LLM chỉ đề xuất phần được phép thay. Body `{revision:Int>=1,parent_model_id:ID|null,source_context_id:ID,created_by_run_id:ID,change_id:ID|null,actors:Actor[],actions:Action[],workflows:Workflow[],data:Data[],rules:Rule[],components:Component[],responsibilities:Responsibility[],interfaces:Interface[],dependencies:Dependency[],mappings:Mapping[]}`.

Revision 1 parent/change null; revision sau parent cùng session, +1 và có Change. Model không chứa diagram/review để tránh vòng tự xác nhận. Collections có thể [] lúc phân tích chưa xong; bundle cần báo thiếu, không gọi đầy đủ. Mỗi phần tử dưới đây có `id`, `trace`, `state` nêu ở mục 2; bảng là **các trường bổ sung**.

| Phần tử; bước tạo → dùng | Trường bổ sung / kiểu | Invariant và trách nhiệm |
| --- | --- | --- |
| Actor; 2 → 2–9 | `name:Text`, `kind:supplied|candidate` | supplied name/ref khớp một actor S01; actor mới candidate có nguồn/câu hỏi, không thêm vào snapshot. LLM đề xuất; code kiểm; user làm rõ |
| Action; 2 → 3–9 | `name:Text`, `initiator:external|internal|unknown`, `actor_ids:ID[]`, `permission_rule_ids:ID[]`, `read_data_ids:ID[]`, `write_data_ids:ID[]`, `rule_ids:ID[]`, `workflow_ids:ID[]` | unknown/internal bắt buộc actor_ids=[]; external bắt buộc actor_ids không rỗng. Vi phạm ⇒ SCHEMA_INVARIANT / schema, invariant `action_initiator_actors`. Actor ID tồn tại không chứng minh có quyền; permission_rule_ids=[] hợp lệ để giữ unknown kèm issue. Không gán actor cho hủy bằng suy quyền xem. read/write [] chỉ chưa ghi nghĩa vụ, không khẳng định không thể phát sinh |
| Data; 2 → 3–7 | `name:Text`, `description:Text` | Khái niệm logic, không bảng DB/ownership/deployment |
| Rule; 2 → 3–9 | `statement:Text`, `kind:business|permission|consistency`, `action_ids:ID[]` | Quyền xem không trở thành quyền hủy. Rule có thể explicit, phân chia thực thi vẫn inferred |
| Workflow; 2 → 3–9 | `name:Text`, `entry_node_id:ID`, `nodes:Node[]`, `edges:Edge[]`, `branch_points:BranchPoint[]` | Node `{id,action_id:ID|null,kind:action|decision|end,label:Text}`; action node có ID action, còn lại null. Edge `{id,from:ID,to:ID,guard:Text|null,trace:Trace}`; endpoints trong workflow, decision edge cần guard; null guard = vô điều kiện. BranchPoint `{node_id:ID,mode:exclusive|unknown,trace:Trace}`: node có ít nhất hai edges ra; exclusive là đề xuất lựa chọn loại trừ nhau cần semantic review. Node không có BranchPoint được duyệt tất cả edges. Guard tự do không chứng minh exclusive/độc lập. Nhánh ngoại lệ thiếu giữ issue, không tự tạo đường thành công |
| Component; 3 → 4–9 | `name:Text`, `purpose:Text`, `grouping_reason:Text`, `alternatives:Text[]`, `uncertainties:Text[]` | Lý do liên quan thao tác/dữ liệu/quy tắc; không mỗi entity=component. [] alternatives là chưa ghi phương án khác, review phải thấy |
| Responsibility; 3–5 → 4–9 | `component_id:ID`, `statement:Text`, `action_ids:ID[]`, `rule_ids:ID[]` | Đúng một component chính cho mỗi responsibility; phối hợp biểu diễn mappings/deps; không copy obligation rồi coi là chứng minh |
| Interface; 5 → 6–9 | `name:Text`, `capability:Text`, `provider_component_id:ID`, `responsibility_ids:ID[]` | Provider tồn tại, responsibilities thuộc provider; chưa có protocol. Required usage nằm ở dependency có interface_id, không phát minh interface từ tên mũi tên |
| Dependency; 5 → 6–9 | `kind:uses_component|requires_interface`, `consumer_component_id:ID`, `provider_component_id:ID`, `interface_id:ID|null`, `capability:Text`, `action_ids:ID[]`, `workflow_ids:ID[]`, `reason:Text`, `support:Support[]` | Hướng consumer→provider, hai đầu khác nhau. uses_component yêu cầu null interface; requires_interface có interface đúng provider. Ít nhất một action/workflow. Support `{action_id:ID,provider_responsibility_ids:ID[],required_action_ids:ID[]|null}`: đúng một entry cho mỗi action_ids; nếu action_ids=[] thì cho mọi action trong workflows được chỉ. Provider responsibilities thuộc provider/interface, không rỗng; required_action_ids null = chưa rõ prerequisite, [] = đề xuất không có action bổ sung, cần review. Thiếu đầu mút là lỗi code; lý do sai nghĩa do review, không suy dependency từ cùng dữ liệu |

Các references nội bộ ID luôn resolve trong model chứa chúng. Tất cả actor supplied được giữ; actor gần giống không tự gộp. LLM không được ghi revision, origin source, kết quả validation, trạng thái review hoặc mutate snapshot. Code không xác nhận tính đúng của rationale chỉ vì là nonblank.

### 5.1 Mapping nghĩa vụ, không chỉ liên kết ID

Mapping không dùng Trace chung vì nguồn nghĩa vụ được định nghĩa tường minh; có `{id,source_ref:SourceRef,parts:Part[],assessment:"not_assessed"|"proposed",issue_ids:ID[]}`. SourceRef trỏ **toàn requirement object hoặc một criterion string**, không text con. Bước 4 tạo đúng một Mapping cho mỗi requirement và **mỗi criterion** trong ba nhóm; missing row là lỗi kiểm kê. Trạng thái đã review chỉ được dẫn xuất từ Review hợp lệ đúng model; không thêm `reviewed` vào model bất biến, không cho LLM tự đặt. `parts=[]` chỉ hợp lệ khi not_assessed và có issue mô tả chưa phân tích; proposed cần ít nhất một part.

`Part={id:ID,obligation:Text,assignment:"proposed"|"unassigned"|"blocked",target:"components"|"system",action_ids:ID[],primary_responsibility_ids:ID[],supporting_responsibility_ids:ID[],covered_portion:Text|null,remaining_gap:Text|null,issue_ids:ID[]}`. action_ids là tập thao tác cụ thể nghĩa vụ phần này bao phủ; components/proposed cần không rỗng, unassigned có thể [] và bị chặn. System có action_ids=[] nghĩa áp dụng cho mọi slice được chuyển tiếp; chọn chính sách bảo thủ, không dùng [] để miễn nghĩa vụ. Muốn giới hạn nghĩa vụ global phải phân tích/sửa model và được review, không đọc prose để tự miễn. Hai responsibility lists unique/disjoint. Components/proposed cần ít nhất một primary; system không ép có component. unassigned/blocked cần remaining_gap; blocked cần open issue. covered_portion null khi chưa có đề xuất bao phủ. Đây là **lập luận bao phủ ở mức model**, không khẳng định runtime đáp ứng. Có thể đề xuất trách nhiệm cho phần lưu lịch sử R2 trong khi quyền khởi phát còn blocked. Toàn text R2 phải được phân tách sao cho lý do/người/thời điểm và giải phóng slot không bị mất; code kiểm mọi row và missing fields, người review kiểm không bỏ sót nghĩa vụ.

## 6. Tình huống và architectural characteristics

Các hồ sơ versioned ngoài model để bước 6 **không sửa model**. LLM phân tích, code quản lý refs/version, người dùng review mục tiêu/đánh đổi. Model_id là bản được xét; không tự carry hồ sơ qua bản khác.

`type=scenario` (bước 5–6 tạo → 6–9 dùng). Body `{analysis_key:ID,supersedes_id:ID|null,model_id:ID,name:Text,trace:Trace,scope:Scope,trigger:Text,conditions:Text[],expected_obligations:SourceRef[],walkthrough:Walk[],assessment:"not_assessed"|"supports_at_model_level"|"gap"|"needs_clarification",issue_ids:ID[],verification_obligations:Text[]}`. `Walk={order:Int>=1,element_refs:ElementRef[],observation:Text}`; order liên tiếp, refs cùng model. Walkthrough là lập luận thiết kế, không có runtime_passed. expected_obligations phải requirement/criterion nguồn; bổ sung inferred phải giữ ở trace/conditions và không đổi nghĩa vụ chuẩn.

`type=characteristic` (bước 6 → 7–9). Body:

| Trường | Kiểu / nghĩa |
| --- | --- |
| `analysis_key`, `supersedes_id` | ID, ID|null; identity/supersession theo §6.1 |
| `model_id`, `name`, `trace`, `scope` | ID, Text, Trace, Scope; name không chỉ giới hạn sáu thuộc tính, nhưng phải có căn cứ/câu hỏi |
| `goal`, `conditions`, `priority` | Text|null; Text[]; `must|should|could|null`; null = nguồn chưa xác định, không tự lấy metric rank làm priority |
| `scenario_ids` | ID[]; scenario cùng model; [] phải ghi thiếu trong issues/verification |
| `boundary_effects` | `{element_refs:ElementRef[],observation:Text,evidence_refs:SourceRef[],assumptions:Text[]}[]`; phân tích ranh giới/trách nhiệm/dependencies hiện tại |
| `options` | `Option[]` ít nhất một; cần so với giữ nguyên khi đề xuất sửa |
| `recommendation` | `keep|change|undecided`; chỉ đề xuất, không tự apply |
| `recommended_option_id` | ID|null; keep/change phải có option tương ứng, undecided null |
| `issue_ids`, `risks`, `verification_obligations` | ID[]; Text[]; Text[]; [] chỉ chưa ghi, không xóa unknowns |

`Option={id:ID,action:"keep"|"split"|"merge"|"move_responsibility"|"change_dependency",description:Text,benefits:Text[],costs:Text[],other_characteristic_impacts:Text[],constraint_refs:SourceRef[],precondition_issue_ids:ID[]}`. Tác động dự kiến, không đo. Constraint R5 vẫn là constraint, không đổi tên thành quality attribute. Câu hỏi mục tiêu thiếu về bước 1; option chưa có điều kiện không được apply như đã đạt. R3 có p95/điều kiện thử; không tạo SLA availability, workload production hay mục tiêu scaling. Không trường score/pass cho chứng nhận runtime.

### 6.1 Tập phân tích đang áp dụng — F01

**Chọn AnalysisSet bất biến và head riêng mỗi session.** `type=analysis_set`, body `{model_id:ID,revision:Int>=1,parent_set_id:ID|null,scenario_ids:ID[],characteristic_ids:ID[],issue_ids:ID[],changed_record_ids:ID[],affected:Scope}`. Source context derive từ model. Model mới bắt đầu AnalysisSet revision1/parent null, commit cùng model; cùng model đổi tập thì +1/parent đúng head hiện hành. Không liên hệ số này với model.revision hoặc S01 revision. Bản đầu có thể chưa có scenarios/characteristics; không coi tập rỗng là đã phân tích đủ.

Scenario/Characteristic có `analysis_key` ổn định theo loại/session; Issue dùng issue_key. Lần đầu supersedes_id=null; thay nhận xét/câu hỏi tạo record mới trỏ **record hiện hành cùng key/type**, không fork, không chọn bằng timestamp. AnalysisSet chọn đúng một record/key; các lists unique và record.model_id đúng model. Mọi key cũ của cùng model phải còn hiện diện, hoặc được thay bởi successor; không xóa hồ sơ để che gap. Issue resolved/withdrawn vẫn được chọn. Characteristic/Scenario không còn áp dụng vẫn giữ record hiện hành, giải thích thay assessment/phạm vi bằng successor, không tombstone âm thầm. Khi model đổi, dựng lại hồ sơ với refs mới và supersedes lịch sử để giữ lineage; history không được chọn thay current record.

Refs tới Scenario/Issue trong hồ sơ **đang áp dụng** phải là ID được tập chọn. Model bất biến có thể pin Issue phiên bản cũ; resolver theo issue_key tìm current record trong AnalysisSet, giữ link gốc để audit. Đây là phép resolve Issue được quy định, không retarget SourceRef. Việc giải quyết Issue không tự bỏ state needs_clarification/needs_reanalysis hay Part blocked trong model; phải sửa model nếu state đó cần đổi. Thay Scenario kéo theo successor của Characteristic đang tham chiếu nó trong cùng lần công bố; thiếu thì từ chối publish, không để set current bị lẫn bản cũ.

`changed_record_ids` đúng các records mới/thay trong set; affected là ít nhất hợp của scope cũ/mới (Issue dùng affected), mở rộng ngược theo closure §9.1: mọi seed phụ thuộc vùng đó đều bị ảnh hưởng. Unknown tác động ⇒ enumerate toàn model/parts, không để scope rỗng. Initial set enumerate toàn model. Change model dùng cơ chế Change/reanalysis đã có; analysis-only thêm issue/task thay đổi set nhưng không mutate model.

Validation pin `analysis_set_id`; Bundle pin cùng ID và scenario/characteristic/issue lists **đúng bằng set**. `freshness=passed` đòi model=head_model, set=head_analysis_set, nguồn khớp và mọi hồ sơ/attestation current; tại lookup/gate phải kiểm lại, không tin cờ passed lịch sử. Diagram/view cùng model có thể dùng lại bytes đã kiểm hash/fidelity trong Validation và Bundle mới; không copy approval/readability sang artifact khác.

**Bản đầu không tự bảo lưu approval một phần khi set đổi**, kể cả affected không giao accepted scope. Phải tạo Validation/Bundle và người dùng review mới; lịch sử review giữ nguyên. Trade-off: review lại nhiều hơn, đổi lại không cần chứng minh acceptance xuyên phiên bản phân tích. Phần phân tích độc lập vẫn có thể được làm tiếp/dùng lại record không đổi, với closure không giao affected, refs current và giải thích reuse trong disclosures; điều đó không giữ approval. `affected` phục vụ tác vụ reanalysis/disclosure, không là cách né gate freshness.

Công bố phân tích/model/Validation/Bundle/Review/Handoff kiểm cặp expected `(base_model_id,base_analysis_set_id)` trong BEGIN IMMEDIATE và CAS hai head. Hai công bố phân tích cùng base: một tạo set mới; bên kia ANALYSIS_CONFLICT, lưu raw/stale, không auto merge. Validation/handoff tính ngoài lock phải kiểm lại cặp trước commit; nếu issue publish trước thì gate cũ fail. Nếu handoff commit trước, nó là kết quả lịch sử tại thời điểm đó; consumer lookup/export kiểm lại heads, không dùng eligible cũ như quyền vĩnh viễn. `session.sequence` chỉ ordinal vận hành tăng khi ghi event/log/review; không là freshness token. Log/lookup/review không đổi set; review supersession có CAS active_review riêng. Thêm record phân tích chưa được publish không có hiệu lực; publish issue phát hiện chặn phải cùng final outcome, không báo đã xử lý rồi giấu nó ngoài set.

### 9.1 Closure phạm vi bàn giao — F04

Scope cho S03 là nghĩa vụ/mapping parts và thao tác cần dùng, không tên component nguyên khối. `WorkflowChoice={workflow_id:ID,node_id:ID,edge_id:ID,independence_evidence:Text}` trong Review; Handoff mang đúng các choices dùng. Node phải là BranchPoint exclusive, edge đi ra node; mỗi node tối đa một choice. Chỉ người review xác nhận lựa chọn nhánh cùng điều kiện và căn cứ độc lập, không code suy từ guard. Unknown branch không được chọn hẹp ⇒ SCOPE_UNDETERMINED. Không có choice thì **duyệt tất cả edges** kể cả exclusive; không mặc định lấy happy path. Bằng chứng independence cần đối chiếu trace/source, dữ liệu/quy tắc/dependencies và condition review; một câu không rỗng chỉ qua cấu trúc, người review chịu trách nhiệm nghĩa.

Thuật toán bắt buộc, hữu hạn trên model + AnalysisSet đã pin:

1. Seeds gồm mapping_part_ids xin tiếp tục và các actions trong element_ids được chọn. Từ **mỗi part components**, thêm toàn bộ Part.action_ids, primary/supporting responsibilities của part. Đây là quy tắc cho **mọi part được đưa vào closure**, không chỉ seeds; part phát hiện trong vòng lặp cũng phải được mở rộng đầy đủ theo bước 3. Không cho chọn ít actions hơn nghĩa vụ part; muốn tách phải sửa Part/model trước review. Các parts system không sinh actions; slice phải có ít nhất một action. Chọn component/interface đơn lẻ không cấp toàn bộ trách nhiệm của nó.
2. Với mỗi action mới, thêm rules/permission rules của action, và rules có action_ids chứa action; thêm workflows khai báo. Các data/actor refs phải hợp lệ nhưng không mở rộng sang mọi action dùng chung data/actor. Trong **mỗi workflow đã chạm**, đi từ entry, duyệt đồ thị node/edge theo choices ở trên; thêm **mọi action reachable trên đồ thị này**, gồm prerequisite trước action được chọn và công việc bắt buộc phía sau. Selected action không reachable dưới choice ⇒ SCOPE_UNDETERMINED. Thêm node vào visited trước khi duyệt tiếp; chu trình xử lý đến fixed point, không bỏ SCC để lách issue. Vòng lặp hợp lệ cấu trúc không chứng minh nghiệp vụ kết thúc; nghi ngờ termination giữ issue.
3. Với mỗi action trong closure, thêm mọi mapping part components có action_ids chứa nó; đây là nghĩa vụ **cần review**, không tự accepted. **Mỗi part mới được phát hiện, dù qua action/workflow/dependency, phải thêm toàn bộ Part.action_ids và primary/supporting responsibilities của chính part đó**, rồi rules/component chủ tương ứng. Mọi action mới từ part phải tiếp tục qua bước 2–5; không chỉ xét action đã làm phát hiện part. Vì vậy P1={A1} gặp P12={A1,A2} phải thêm A2, rồi phát hiện P2={A2} cùng mọi phụ thuộc/blocker của A2. Mapping thiếu/unassigned/blocked hoặc action không có part/trách nhiệm đủ căn cứ ⇒ gate chặn, không đoán nghĩa vụ. Chỉ mở rộng các actions do **Part khai báo là cùng một nghĩa vụ**; không mở rộng mọi action của component/responsibility/interface dùng chung. Muốn xét A1 độc lập, phải tách P12 thành các parts phù hợp trong model mới trước review; gate không tự cắt part bằng prose.
4. Duyệt Dependency khi action_ids giao actions hiện có; dependency chỉ ghi workflow_ids (action_ids=[]) áp dụng cho tất cả actions của workflows được chạm. Không thêm mọi responsibility của provider hoặc mọi action của interface. Thiếu entry/type/provider link ⇒ lỗi cấu trúc; không dùng text capability để tự suy. Nhiều tầng và vòng dependency cùng dùng visited/fixed point, không limit chiều sâu rồi cho qua.
5. Thêm **tất cả parts target=system** vào nghĩa vụ bắt buộc cho mọi slice, gồm NFR/constraints và criteria tương ứng; không suy ngoại lệ từ priority, view hoặc chỉ từ ví dụ R3/R5. Phải review rõ chúng cho actions trong closure và giữ điều kiện verification phù hợp. Muốn hạn chế applicability cần model mới có phân tích/căn cứ và review, không tự miễn ở gate. Requirements/criteria thiếu row/part vẫn lỗi inventory. Đây là quy tắc bản đầu bảo thủ, có thể yêu cầu review nhiều hơn nghĩa vụ thật sự liên quan.
6. Lặp 2–5, gồm cả quan hệ **part→toàn bộ actions** ở bước 3, tới khi actions/parts/support-context không tăng và không còn action/part mới chưa được xử lý. Dùng tập đã xử lý theo ID trên model hữu hạn; gặp lại part/action không tạo công việc vô hạn, nhưng không được đánh dấu một part đã xử lý trước khi thêm đủ actions của nó. Tại fixed point, với mọi part components trong closure phải có `set(part.action_ids) ⊆ closure.actions`; đồng thời mọi part chứa action trong closure và mọi phụ thuộc ở bước 2–5 đã được xét. Chỉ kiểm gate sau khi đạt closure đầy đủ, không bỏ A2 để né blocker. Kiểm closure giao current Issue.blocking, states needs_clarification/needs_reanalysis, reevaluate pending, blocking Review.conditions và mọi part chưa nằm trong Review.accepted_scope. Issue pin bản cũ resolve current theo §6.1; acknowledged không xóa blocker. Không đủ chứng cứ độc lập cũng chặn. Context chung (component/interface/responsibility) trong Issue.blocking nghĩa block **mọi use** của element đó; muốn chỉ block action cụ thể phải scope issue vào action/part, không block cả interface rồi miễn qua prose.
7. Tính cho từng functional seed part; chỉ giữ seed nếu toàn closure của nó được accepted và không bị chặn. Hợp các closure đạt thành allowed_scope, rồi kiểm lại hợp đó đóng dưới **mọi** quan hệ bước 2–5, đặc biệt mỗi part trong hợp có đủ toàn bộ actions và phụ thuộc đã được xét. Không để một part thiếu closure hoặc bị chặn lọt vào kết quả qua seed khác. Nếu kiểm hợp phát hiện phần thiếu, tiếp tục mở rộng và kiểm lại acceptance/blockers của toàn bộ phần bổ sung trước công bố; không tự coi chúng accepted hoặc xóa action để giữ eligible. Parts system chỉ đi kèm ít nhất một functional part, không tự tạo handoff global-only. Những nghĩa vụ còn lại là blocked_scope; shared supporting context được liệt kê bên allowed nếu có use hợp lệ, phần use bị chặn giữ action/part ở blocked. False ⇒ allowed rỗng; true ⇒ ít nhất một functional part. Nếu prerequisite A2 chặn thì A1 phụ thuộc cũng ở blocked dù user chỉ chọn A1. Giữ reason code và scope thực tế, không âm thầm bỏ A2 để cho A1 qua.

Phạm vi impact ở §6–7 dùng closure này theo chiều ngược: seed nào có closure giao phần đã đổi thì phải xét lại. Nếu branching/support chưa đủ, đánh dấu needs_reanalysis toàn vùng chưa chứng minh độc lập; code không tự tạo bằng chứng ngữ nghĩa. Hai nhánh chỉ tiếp tục độc lập khi choice exclusive đã được biểu diễn/review và closure không gặp blocker; nếu không có cách biểu diễn chọn nhánh, duyệt toàn workflow hoặc yêu cầu làm rõ, không đọc guard tự do để phân nhánh hộ. Tính closure hợp lệ vẫn không chứng minh LLM đã liệt kê đầy đủ dependencies; reviewer đối chiếu nguồn.

File08 giữ bảy graph cũ và thêm ba graph Part nhiều actions tại `/scenarios/7`, `/scenarios/8`, `/scenarios/9`: bị chặn, đủ closure khi không bị chặn, và tách part trong model mới cần review mới. Các ví dụ file08 là **synthetic graphs**, không bổ sung nghiệp vụ phòng khám. R3/R5 trong file04 minh họa quy tắc global tổng quát. S03 chỉ là định nghĩa cổng; chưa implementation S03.

## 11. Lỗi và ngăn kết quả không hợp lệ

`Error={code:Text,stage:"intake"|"parse"|"schema"|"references"|"revision"|"llm"|"render"|"review"|"persistence",record_id:ID|null,pointer:string|null,related_ids:ID[],message:Text,details:object}`. Pointer từ record JSON bị xét; parse/system chưa có cây thì null. details chỉ trường an toàn có quy định theo code bên dưới; không copy Unicode không serialize được vào lỗi lặp lại. Raw bytes vẫn archive khi kho hoạt động. Validation lỗi không được cung cấp một candidate như model committed/handoff eligible.

| Code / stage | details bắt buộc | Kết quả / nơi sửa |
| --- | --- | --- |
| SOURCE_NOT_FOUND, SOURCE_NOT_ELIGIBLE / intake | `run_id:ID,reason:Text` | Không tạo SourceContext trusted; lookup/sửa chọn nguồn, không submit lại |
| UNSUPPORTED_VERSION / intake hoặc schema | `received:Text,supported:Text[]` | Chặn; không tự migrate |
| INVALID_JSON, DUPLICATE_KEY / parse | `reason:Text` | Không dùng parsed output; vòng repair nếu LLM còn ngân sách |
| SCHEMA_INVARIANT / schema | `invariant:Text` | Invariant xuyên trường S02; unknown/internal với actors không rỗng, external với actors rỗng đều bị chặn |
| ANALYSIS_CONFLICT / revision; ANALYSIS_STALE / review | `expected_analysis_set_id:ID,provided_analysis_set_id:ID` | Công bố base-set lỗi thời bị conflict; bundle/review/handoff của tập cũ bị stale dù model vẫn head |
| SCOPE_UNDETERMINED / review | `scope:Scope,reason:Text` | Nhánh/support chưa đủ để chứng minh closure; không tự thu hẹp phạm vi |
| APPLICATION_CONFLICT / revision | `answer_id:ID,reason:Text` | Diễn giải/consent/base không còn phù hợp hoặc đã apply; lookup lịch sử, không submit lại S01 |
| SCHEMA_INVALID / schema | `keyword:Text,expected:Text` | Đúng bước tạo; không coerce/default/strip |
| SOURCE_REF_INVALID / references | `snapshot_id:ID,input_pointer:string,expected_kind:Text` | Chặn ref thiếu/sai loại/snapshot; sửa mapping, không retarget |
| ELEMENT_REF_INVALID / references | `model_id:ID,element_id:ID` | Endpoint/ID sai; không thêm node để render |
| MAPPING_INVENTORY_INCOMPLETE / references | `missing_refs:SourceRef[]` | Bước 4; khác với thiếu nghĩa vụ ngữ nghĩa bên trong row |
| MODEL_CONFLICT, STALE_OUTPUT / revision | `expected_model_id:ID|null,provided_model_id:ID|null` | Lưu attempt stale; không apply/auto merge |
| NEEDS_REANALYSIS, BLOCKED_SCOPE / revision | `scope:Scope,issue_ids:ID[]` | Chặn phần phụ thuộc, cho phép phần độc lập theo gate |
| VIEW_NOT_CLOSED / references | `missing_ids:ID[]` | Sửa view, không sửa nghĩa model |
| DIAGRAM_LABEL_UNREPRESENTABLE, RENDER_FAILED, FIDELITY_MISMATCH / render | `reason:Text` | Diagram không ready, giữ artifact lỗi, sửa converter/layout |
| REVISION_MISMATCH / review hoặc references | `expected_model_id:ID,provided_model_id:ID` | Không nhận diagram/review của bản khác |
| REVIEW_GATE_FAILED / review | `reason:Text` | Chưa review/waive lỗi cấu trúc/phạm vi không độc lập ⇒ handoff false |
| LLM_FAILED, BUDGET_EXHAUSTED, NO_PROGRESS / llm | `reason:Text` | Không tự accepted, giữ issue/attempt |
| PROCESSING_FAILED / schema hoặc persistence; PERSISTENCE_FAILED / persistence | `reason:Text` | failed, không công bố commit chưa đối soát; lookup run mới connection |

Lookup lịch sử không tạo run/revision/timestamp mới. Không tìm thấy ≠ đã rollback. Lock timeout là persistence failed, không MODEL_CONFLICT. Trạng thái commit chưa rõ đối soát command ID/event rồi Run ID nếu finalized, không tự retry như submit mới. Chuỗi exception không serialize được được thay bằng diagnostic cố định an toàn **ở metadata lỗi**, không sửa nội dung nguồn. Không có API nhập nguyên Record để người gọi tự ghi validation/review/handoff: adapter chỉ nhận command/candidate/answer/decision trong quyền tương ứng; records nguồn và kết quả gate do code lookup/kiểm trước ghi. Contract này không tuyên bố idempotency API.
